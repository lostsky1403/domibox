# ADR-009: Model Otentikasi dan Otorisasi (Single-Owner & Temporary Access Token)

---

## 1. Konteks & Masalah (Context)
DomiBox adalah aplikasi *self-hosted* yang beroperasi di bawah asumsi awal **single-owner** (`A-002`, `A-006`) dan tidak ada registrasi publik (`A-003`). Model autentikasi harus melindungi seluruh operasi manajemen administratif (domain, akun permanen, konfigurasi) dan menyediakan akses terbatas ke mailbox sementara yang dibuat publik oleh pengguna (link inbox disposable).

---

## 2. Faktor Pendorong Keputusan (Decision Drivers)
1. **Proteksi Kontrol Penuh Administrator:** Akses ke API manajemen domain, pengaturan sistem, dan mailbox permanen harus dibatasi ketat (`SEC-001`).
2. **Isolasi Akses Mailbox Sementara:** Akses ke inbox sementara harus terbatas hanya pada pemegang token, tanpa memerlukan akun otentikasi penuh (`SEC-004`, `FR-002`).
3. **Keamanan Sesi Web & Bot:** Sesi login web harus terlindungi cookie HttpOnly/SameSite; bot Telegram harus diverifikasi melalui ID pengguna yang di-whitelist (`SEC-005`, `SEC-006`).

---

## 3. Pilihan yang Dipertimbangkan (Options Considered)

| Parameter Evaluasi | Opsi 1: Token Admin + Mailbox Access Token (Dipilih) | Opsi 2: Full Account & RBAC Sejak Awal | Opsi 3: Tanpa Otentikasi (Public Access) |
| --- | --- | --- | --- |
| **Kompleksitas Implementasi** | Rendah–Sedang (Sesuai MVP scope) | Tinggi (Over-engineering untuk single-owner) | Rendah (Tidak aman) |
| **Tingkat Keamanan** | Kuat untuk kebutuhan privat | Sangat Kuat (untuk multi-tenant) | Nol |
| **Dukungan Mailbox Sementara** | Sangat Baik (Access token per mailbox) | Rumit (perlu akun tamu anonim) | Tidak terkendali |

---

## 4. Keputusan yang Diambil (Decision Outcome)
Memilih **Opsi 1: Model Otentikasi Hibrida (Admin Session + Temporary Mailbox Access Token)**.

1. **Akses Administrator (Web Dashboard & Telegram):**
   - Login web menggunakan *email/password master* yang di-hash (Argon2id) di PostgreSQL. Sesi disimpan sebagai *HttpOnly, Secure, SameSite=Strict cookie*.
   - Telegram bot melakukan verifikasi terhadap daftar Telegram User ID yang diizinkan (`OWNER_TELEGRAM_IDS` di environment variable atau tabel konfigurasi). Command dari ID lain ditolak secara otomatis.

2. **Akses Mailbox Sementara (Disposable Inbox):**
   - Saat mailbox sementara dibuat, sistem menghasilkan token akses acak kriptografis (minimum 128-bit entropy) yang disimpan di database (hash/representasi aman sesuai implementasi).
   - **Transport token kanonis:** klien dapat menyertakan token sebagai (a) query parameter `token=<access_token>` pada tautan inbox yang dapat dibagikan (`/inbox/:mailboxId?token=...`) atau (b) header HTTP `X-Mailbox-Token: <access_token>` untuk pemanggilan API terprogram. Server menerima salah satu bentuk tersebut pada endpoint baca mailbox/pesan yang diizinkan untuk akses guest mailbox; implementasi API dan OpenAPI harus mendokumentasikan skema ini secara eksplisit.
   - Tanpa token valid yang terikat ke mailbox terkait, akses ditolak (`SEC-004`).
   - Token ini juga dikirimkan ke Telegram sebagai link aman untuk membuka inbox.

3. **Otorisasi Granular:**
   - Admin memiliki akses penuh ke semua endpoint `/api/v1/*`.
   - Mailbox Access Token hanya diizinkan untuk endpoint baca pesan dan OTP dari mailbox spesifik miliknya (`GET /api/v1/mailboxes/:id/messages`, dll.).

---

## 5. Konsekuensi Positif & Negatif (Consequences)
### Konsekuensi Positif:
- Implementasi cepat dan aman untuk fase MVP single-owner.
- Mailbox sementara tetap aman dari akses publik liar tanpa token.
- Tidak memerlukan arsitektur multi-tenant yang kompleks sebelum dibutuhkan.

### Konsekuensi Negatif & Mitigasi:
- *Token mailbox di URL bisa bocor via referrer log jika tidak hati-hati:*
  - *Mitigasi:* Frontend dikonfigurasi dengan `Referrer-Policy: no-referrer` dan token dikirim sebagai query parameter hanya pada tautan langsung (bukan diklik dari halaman pihak ketiga).
