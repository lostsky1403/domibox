# ADR-012: Strategi Sinkronisasi Real-time (SSE/Polling) Web Dashboard

---

## 1. Konteks & Masalah (Context)
Web Dashboard DomiBox harus menampilkan email masuk baru dan kode OTP yang terdeteksi secara *near real-time* tanpa memerlukan pengguna melakukan refresh halaman manual (`FR-003`, `FR-005`, `UI-004`). Backend harus mendorong atau menyediakan mekanisme pembaruan data ke klien web.

---

## 2. Faktor Pendorong Keputusan (Decision Drivers)
1. **Latensi Notifikasi Rendah:** Pesan baru/OTP harus terlihat dalam waktu singkat setelah diterima mail server (target < 5 detik end-to-end ke UI).
2. **Kesederhanaan Implementasi & Infrastruktur:** Tidak memerlukan broker pesan tambahan (Redis Pub/Sub terpisah, WebSocket gateway kompleks) pada fase MVP.
3. **Kompatibilitas dengan Fastify & Browser Modern:** Solusi harus mudah diintegrasikan dengan backend Fastify dan didukung browser tanpa library klien berat.

---

## 3. Pilihan yang Dipertimbangkan (Options Considered)

| Parameter Evaluasi | Opsi 1: Server-Sent Events (SSE) (Dipilih) | Opsi 2: WebSocket (Full Duplex) | Opsi 3: Short Polling Berkala |
| --- | --- | --- | --- |
| **Arah Komunikasi** | Satu arah (Server → Client), cukup untuk notifikasi | Dua arah (tidak diperlukan untuk kasus ini) | Satu arah (Client pull) |
| **Kompleksitas Backend** | **Rendah** (Native HTTP, endpoint stream) | Sedang (perlu manajemen koneksi WS) | **Rendah** |
| **Efisiensi & Latensi** | **Baik** (koneksi persisten, push instan) | Baik (koneksi persisten) | Buruk (delay interval polling, beban request berulang) |
| **Kebutuhan Infra Tambahan** | Tidak ada | Tidak ada (tapi manajemen state lebih rumit) | Tidak ada |

---

## 4. Keputusan yang Diambil (Decision Outcome)
Memilih **Opsi 1: Server-Sent Events (SSE)** sebagai mekanisme utama untuk notifikasi real-time di Web Dashboard.

- **Endpoint SSE:** `GET /api/v1/events` (autentikasi via session cookie admin atau mailbox access token).
- **Event Types:**
  - `message.received`: Payload ringkas berisi `mailboxId`, `messageId`, `sender`, `subject`, `receivedAt`.
  - `otp.detected`: Payload berisi `messageId`, `otpCode`, `expiresAt` (jika relevan).
- **Fallback:** Jika koneksi SSE terputus atau browser tidak mendukung, klien melakukan polling interval 10 detik ke `GET /api/v1/mailboxes/:id/messages`.

Implementasi backend:
- Fastify endpoint menggunakan `reply.raw` atau plugin SSE untuk mempertahankan koneksi HTTP terbuka.
- Event internal dipicu setelah pesan berhasil diparsing dan disimpan ke PostgreSQL oleh worker pemrosesan inbound.

---

## 5. Konsekuensi Positif & Negatif (Consequences)
### Konsekuensi Positif:
- Implementasi sederhana di atas HTTP standar (auto-reconnect bawaan browser via `EventSource`).
- Overhead server rendah dibanding polling dan lebih sederhana dari WebSocket untuk kebutuhan satu arah.
- Tidak memerlukan dependensi infrastruktur tambahan.

### Konsekuensi Negatif & Mitigasi:
- *Batas koneksi konkuren browser/proxy:* Browser membatasi koneksi HTTP/1.1 per domain (umumnya 6). SSE memakai satu koneksi persisten.
  - *Mitigasi:* Gunakan HTTP/2 (via Caddy/Nginx) yang memultiplexing koneksi. Untuk single-owner, batas ini tidak menjadi masalah.
- *Satu arah saja:* Klien tidak bisa mengirim data via SSE (tidak diperlukan; aksi klien tetap via REST POST/DELETE).
